# 从资料到成稿

三条入口共用一套文件：`brief.md → sources.md → outline.md → draft.md → preview.html`。不要跳过台账直接写；也不要把台账做成给用户看的报告。

## 三种入口

| 入口 | 用户给的 | 你多做的一步 |
|---|---|---|
| 资料成文 | 文件、链接、粘贴的材料 | 先读材料，再决定还缺什么 |
| 描述成文 | 一句描述、一个题目 | 自己检索、落账、再写 |
| 草稿修订 | 已有 `draft.md` | 先诊断（主线/证据/节奏），再决定改哪层 |

三种入口都可能叠加语气档案。开始前先确认有没有档案（`voice show`）；有就按档案写，没有就按中性中文写，不要为此停下来问。

## 先把材料读成文字

- `md / txt` 直接用 `read` 读。
- `docx / html / rtf` 用 `python scripts/writing.py extract <文件> --out research/<名字>.md`，再读抽出来的 Markdown；不要凭文件名猜内容。
- `pdf` 先转成 `docx` 或 `md`（PDF 取文本容易丢段落、脚注和标点），转换后核对一遍段落顺序。
- 图片、扫描件先用 OCR 或让用户补文字；读不出来的部分标 `〔待核：原件第 N 页无法识别〕`，不要靠上下文补。
- 材料里的表格、附件、脚注常常是关键数据所在，抽完检查有没有丢。

## 开工只问三个问题

默认只确认三件事，其余按假设写，并在交付时说明假设：

1. **题眼**：这篇只回答哪一个问题？（不是「主题是什么」，是「读完能回答什么」）
2. **读者与场景**：写给谁看，发在哪？（决定语域、篇幅、术语密度）
3. **篇幅与截止**：多少字、什么时候要？（决定检索深度和结构）

以下情况才多问：

- 材料互相矛盾，且用户没说以哪份为准。
- 涉及具体数字、金额、人名，材料里没有，且不能标 `〔待核〕`（例如要对外发布的正式稿）。
- 用户明确要求「先别写，先跟我对大纲」。

**不该问的**：

- 文体已经能从材料看出来（有标题、有栏目、有旧稿）。
- 用户说「你看着办」「简单写写」。
- 已经在对话里回答过的问题。

把回答写进 `brief.md`；没回答的写进「假设」，交付时一句话说明。

## 来源台账

`sources.md` 一条主张一行，列和模板一致：

| # | 主张（成稿里怎么说） | 来源（发布者 · 标题） | 日期 | 原文摘录 / 转述 | 链接 | 可信度 | 用在哪节 |

### 记录规则

- **原文摘录逐字**。复制粘贴，不改标点、不合并句子。摘录超过 200 字时截取关键句，用 `……` 标记省略。
- **转述标「转述」**，并写清转述依据的原句位置（段落/小标题）。转述不能加引号。
- **日期写发布或数据截止日期**，不写你抓取的日期。没有日期就写「无日期」。
- **可信度**：一手（原始文件、统计公报、公司公告、当事人发言）> 权威（有编辑流程的媒体、研究报告）> 二手（转述、聚合、自媒体）。二手来源只能用来找线索，不能单独支撑关键事实。
- **用在哪节**：写小节号。没有去处的主张先不进台账，避免材料堆着不用。
- 一条来源支撑多条主张时，拆成多行，共用同一个链接；不要一行里塞三件事。

### 材料冲突

两份材料对同一事实说法不同：

1. 都记进台账，标「冲突」。
2. 判断是不是口径不同（统计范围、时间、定义），写清差异。
3. 正文里要么并列两说并注明，要么采用更一手的一份并说明理由；不要平均成一个模糊说法。
4. 判断不了就标 `〔待核：两种说法冲突，A 说…，B 说…〕` 并告诉用户。

## 检索流程（描述成文）

### 1. 收窄

把题目变成一句可回答的问题：

- 题目：「AI 对写作的影响」
- 收窄：「过去两年，AI 工具先改变了中文内容团队的哪个环节？」
- 判断假设：「先变的是初稿生产，不是审稿和分发。」

题目太大时自己收，并在 `brief.md` 写「本次只覆盖 X，不覆盖 Y」。收窄不是缩小价值，是让文章有可验证的落点。

### 2. 设计查询

四类各至少一条，写进 `brief.md` 或 `research/plan.md`：

| 类型 | 目的 | 查询示例 |
|---|---|---|
| 官方/一手 | 拿到可引用的原始说法 | `site:gov.cn 生成式人工智能 服务管理 办法`、公司公告、年报 |
| 数据 | 找到可核对的数字 | `2025 中国 网络文学 市场规模 报告` |
| 反例 | 避免只找支持自己的证据 | `AI 写作 版权 争议`、`AI 生成内容 失败案例` |
| 背景 | 解释为什么现在发生 | `2024 2025 内容行业 人力 成本 变化` |

时间窗写清楚：默认近 2 年；历史题按事件时间；政策题看生效日期而不是发布日。

### 3. 执行与落账

- `web_search` 只用来找线索；**每条要用的主张都打开原文**。搜索摘要、标题、AI 概览都不算来源。
- 优先读：原始文件、官方通报、公司公告、统计公报、有署名和编辑流程的报道。
- 每读完一条，立刻落进 `sources.md`；不要先攒在脑子里。
- 需要引用的句子，复制原文；不要边读边改写，否则回头分不清原话和转述。
- 记录「这条不支持我的假设」的来源——反例比支持证据更能让文章站住。

### 4. 停车条件

满足以下三条就停止检索，开始写：

1. 每个关键主张有一手来源，或两个互相独立的可靠来源。
2. 至少看过一个反例或最强反对意见。
3. 连续两条新查询没有带来新信息。

不要为了「更全面」无限检索。资料越多，越容易写成资料汇编；文章的判断来自取舍，不是来自穷举。

### 5. 失败处理

| 情况 | 怎么办 |
|---|---|
| 打不开、404 | 换官方/镜像/转载，但在台账标「原链接失效」；不要凭标题引用 |
| 付费墙 | 只用可核实的摘要和公开段落，标「仅见摘要」；关键结论标 `〔待核〕` |
| 没有日期 | 标「无日期」；正文里避免用「最近」「近日」 |
| 只有二手转述 | 继续找一手；找不到就在正文里写「据 X 转述」，并降低确定程度 |
| 数据口径不明 | 写清口径，或不用这个数字 |

## 大纲

分析型任务先读 `analysis-playbook.md`；提纲是扩写前的检查点，要交给 `writing_save_outline`。`outline.md` 至少包含：

```
主线（一句话）：
读者读完要带走的一个判断：

## 1. 这一节要回答的判断 / 问题
判断：
证据：哪条台账、哪组数字、哪个反例
条件：什么情况下判断不成立（预测稿必填）
- 待补：
```

不是预测稿时「条件」可以省略；不要为了格式硬填。用户给了判断数或角度时，按用户的来，不为凑节数硬加。

### 功能，而不是标题堆叠

每节只承担一个功能：交代背景、提出判断、展开论据、给案例、处理反例、收束。两节功能相同就合并；某节既不推进主线也不提供必要信息就删。

### 开头四型（选一个，不要四个都用）

1. **场景**：一个具体的人、时刻、动作。适合观察、评论、人物。
2. **数据**：一个能改变读者预期的数字，必须带来源和口径。
3. **问题**：读者真正会问的问题，不是修辞问句。
4. **判断**：直接给结论，但留分寸；后面必须拿证据顶住。

开头不要预告「本文将讨论……」；第一段就进入事情本身。标题之后不要再复读标题。

### 结尾三型

1. **边界**：说清已经发生到哪一步、还没发生什么。
2. **动作**：落到一个具体的人可以做的下一步，或一个正在发生的变化。
3. **未解**：留下真正没答案的问题，不喊口号。

不要用「未来已来」「这只是开始」「新时代」收尾；也不要用「下一篇我们聊……」做预告。

### 结构不要每节同形

全文多数小节如果都是「定义 → 三个分点 → 拔高一句」，读到第三节读者就能预测第四节。至少换两节走法：

- 历史推进：从怎么演变到今天写起。
- 误解澄清：从读者熟悉的错认入手。
- 约束递进：沿着限制一层层揭开。
- 案例切入：先写失败或具体的一个人。

## 逐节写

### 一段一个功能

段落的第一句承担这一段的判断或事实，后面的句子展开、限定、举例。不要一段里换三个话题。段落结尾不要每次都拔高；可以停在事实上。

### 先事实后判断

- 先给可核对的事实、机制、成本、约束，再给判断。
- 判断句要能指出依据；不能的话改成问题或删掉。
- 因果要谨慎：「相关」不写成「导致」；「计划」不写成「已经」；「可能」不写成「必然」。

### 数字、时间、名称

- 数字带口径和来源：`2025 年国内游戏市场实际销售收入 3257.6 亿元（中国音数协，2025 年 12 月）[3]`。
- 日期写完整：`2026 年 2 月 26 日`，不写「近日」「前不久」。
- 机构名第一次出现用全称，后文再用简称；简称在第一次出现时说明。
- 人名、职务、机构以官方发布为准；不确定就写「时任……」或标 `〔待核〕`。

### 引文

- 直接引语逐字，用引号，注明说话人、场合、时间。
- 译文引文标「译文」；不要把自己的翻译伪装成原话。
- 长引文（超过 60 字）单独成段并缩进；能转述就转述，引文只留最关键的判断。

### 引用样式

**行内归属 + 文末参考资料，正文不出现编号**（分析型 / 随笔的默认写法；深度研究型允许改成「文中编号 + 文末一一对应」，见 `deep-research.md`）：

```
正文：根据《2025 中国数字娱乐产业 IP 发展报告》，……市场规模达 753 亿元。
      另有行业调研表明，2025 年 50.3% 的玩家对游戏 IP 的消费有所增加。
      据宝可梦公司官网公布的数据，截至 2026 年 3 月，系列软件全球累计出货超 5.15 亿份。

文末：
## 参考资料

1. 《2025 中国数字娱乐产业 IP 发展报告》，2026 年 9 月，https://…
2. 宝可梦公司官网「公司数据」页，2026 年 3 月，https://…
```

- 归类短语：根据《X》报道 / 据 X 报道 / 据 X 统计 / X 数据显示 / X 披露 / 据 X 估算 / 据 X 官网公布的数据。
- 一段里出现第二个来源时，写「另有……显示」，不要连着两句都用「根据」。
- 二手转述写「据 X 转述」，不冒充一手。
- **不要**用 `[1]`、`①②`、`（数据来源：…）`，也不要把上标编号当装饰。
- `sources.md` 台账可以带序号（方便自己核对），成稿里不出现。

需要脚注或作者-年份时，在 `brief.md` 里说明并全篇统一；不要和行内归属混着用。

### 不确定的表达

- 证据有限：写清范围和条件（「在……口径下」「目前公开信息只覆盖……」）。
- 趋势明显但程度不确定：说「先影响谁、怎么影响」，不写「彻底改变」。
- 自己的推断：标「我的判断是」「更可能是」，与事实句分开。

## 用户自己写、你给反馈

用户可能只写了一段让你看。按节反馈，不要重写全文：

```markdown
## 这节做对了什么
- （具体到句子）

## 建议
### 清晰
- 原句 → 改法 → 为什么
### 推进
- 这节和主线的连接 / 可以删或并的段
### 证据
- 哪个判断还没有依据，补什么来源

## 可以直接换的说法
> 原句
> 建议句
```

先问「你想让我改，还是只给意见」。用户只要求意见时，不要动文件。

## 文体差异

| 文体 | 要点 | 容易写坏的地方 |
|---|---|---|
| 行业观察 | 一个判断 + 机制 + 数据 + 反例 | 写成资料汇编；每个判断都没有反例 |
| 评论 | 立场清楚，论据跟上 | 开头很猛，后面发虚；结尾再拔高一层 |
| 教程 | 步骤、条件、失败处理 | 只写顺利路径；缺版本和前置条件 |
| 人物/案例 | 先让人物或案例站住，再外推 | 开头人物特写，结尾行业报告，两截拼贴 |
| 通讯/newsletter | 一件主事，几条短讯，语气轻 | 每条都写成小论文；没有主次 |
| 内部报告 | 结论先行，事实与建议分开 | 把建议写成事实；口径不清 |

法定公文（通知、请示、报告、纪要等）不在本模块写，交给 `official-document-drafting`。本模块可以写讲话稿、汇报材料这类非文种材料，但要先确认单位模板要求。

## 交付前

1. `check`：文末参考资料、行内归属、占位符、无署名归因、绝对判断、引号混用、正文残留的引用编号。
2. 逐条回查：每个数字、日期、引文在 `sources.md` 有对应行；引文逐字。
3. 读一遍开头和结尾：开头提出的问题，结尾回应了吗？
4. `render`：预览页能打开、能选中、能出按钮。
5. 交付说明：语气档案、假设、待核点、来源数量。不要贴全文。

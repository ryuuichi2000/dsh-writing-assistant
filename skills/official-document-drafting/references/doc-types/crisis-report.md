# 危机处置报告（crisis-report）

- 类别：常见正式材料
- 别名：危机处置报告、危机报告、处置报告、整改报告
- 适用：发生安全事件、突发事件，或收到主管部门整改通知、通报后，向相对方报告事件总体情况、具体经过和整改情况。
- 字体/版式方案：`official-standard` / `official-standard`

## 快速输入（推荐）

用户选中本模板后，可直接贴下面四项，模型据此起草：

```text
事件主体：
相对方：
主要经过：
处置结果：
```

缺项时先问；用户只说“帮我写一份危机处置报告”时，按“事件主体、相对方、主要经过、处置结果”四项逐项追问，不要先写。

## 起草前确认

至少向用户确认以下四项；缺项先问，问不到再留占位符：

- **事件主体**：报告单位的全称、主要业务或管理范围。
- **相对方**：主送单位，通常是主管部门、监管单位、上级机关或事件相关方。
- **主要经过**：事件如何发现、发生时间、涉及的系统/场所/人员、原因、影响范围、已采取的处置动作。
- **处置结果**：事件是否控制、风险是否消除、有无数据/人员/财产损失、是否已整改完成。

建议补充：

- 事件名称、发现或接报时间、报告时点。
- 整改措施（制度、技术、人员、监测、问责）及完成时限。
- 落款单位、成文日期、是否需要加盖公章。

## 输入与补写规则

用户只给“事件主体、相对方、主要经过、处置结果”时，按以下方式补写：

1. **标题、开头、结尾、落款**由模板生成，不要求用户提供。
2. **事件总体情况**：用 1 段概括“谁、在什么时间、发生了什么事、如何发现、影响范围、当前后果”。只使用用户提供的事实；后果不确定时写 `[待核实]`。
3. **具体经过**：把“主要经过”按“发现与报告—核查与原因—影响确认—现场处置”重组为 3—4 个层次。可以调整顺序、合并重复、补过渡句，但不得增加新事实、新时间、新系统、新人员。
4. **整改情况**：先写“处置结果”，再写“整改措施”，最后写“下一步工作”。处置结果只写用户确认的内容；整改措施可以写与事件类型匹配的通用管理动作（如完善制度、加强监测、开展培训），但不得编造已经完成的具体事项、具体数字或具体责任人。
5. **语气**：对主管部门报告，事实清楚、态度诚恳、措施具体，不辩解、不甩锅、不写空泛口号。
6. **事实缺口**：统一用 `[待核实]` 或 `[具体时间]`、`[责任部门]` 等占位符，不猜测。

## 撰写思路

- **开头**：交代接报/发现时间、相对方、事件名称，一句说明已启动核查处置，用“现将核查与处置情况报告如下”转入主体。不要照抄某一家的开场句式。
- **一、事件总体情况**：先交代事件主体和业务范围，再写事件类型、发生时间、发现方式、影响范围、当前后果。这一段回答“发生了什么、严重程度如何”。
- **二、处置经过**：按时间线或处置环节展开，写清“怎么发现、怎么核查、原因是什么、影响了什么、现场做了什么”。小节按内容命名，不必套固定四段；原因暂时无法确定的，写“正在进一步核查”，不下结论。
- **三、整改情况**：先给处置结果，再列整改措施，最后写下一步。整改措施分条写，尽量落到制度、技术、人员、监测、问责五个维度；每条写清做什么、谁负责、何时完成。
- **结尾**：`特此报告。`
- **落款**：事件主体全称 + 成文日期；盖章按本单位模板处理。

## 写作规则

- 整体骨架是“标题—主送单位—开头—事件情况—处置经过—整改情况—特此报告—落款”；内部小节随内容组织，两种常见排法：时间线（发现—核查—处置—整改）或问题线（事实—原因—影响—整改），不写成事故调查报告、情况通报或请示。
- 事件总体情况只作概括，不铺陈背景；具体经过按事实和时间线写，不写与处置无关的日常工作和成绩。
- 原因分析要有依据；只有用户材料明确支持时才写“系……导致”，否则写“经初步核查，疑似/可能……，正在进一步核实”。
- 影响范围写清业务、数据、人员、设备、第三方等维度；没有造成损失的，明确写“未造成……”，不要含糊。
- 整改措施要与事件原因对应，避免“加强领导、提高认识”式空话；能写完成时限和责任部门的要写实。
- 涉及主管部门通知、通报的，开头点明来文名称或事项；文号、日期不确定的留占位。
- 涉及个人信息、账号、IP、漏洞细节、攻击工具的，按保密要求脱敏或省略，不在报告中完整披露。
- 结尾用“特此报告”，不用“妥否，请批示”。
- 成文日期用阿拉伯数字，年份写全，月日不补零。

## 常见误写

- 写成“情况汇报”或“工作总结”，大段写日常工作和成绩，事件经过和整改反而很少。
- 把尚未查清的原因写成确定结论，或把“可能”写成“就是”。
- 整改措施只有“高度重视、加强管理”，没有具体动作、责任和时限。
- 把主管部门的通知内容大段抄进报告，或把内部敏感细节、IP、账号、漏洞利用方式原样写出。
- 结尾使用“请批示”“请批准”，把报告写成请示。
- 事件主体、相对方、日期前后不一致。

## 脱敏说明

本模板参考过一份真实单位整改报告，只取文体惯例（报告类文书的要素与语气），**分节方式和句式都没有照搬**。原报告中的以下信息已全部替换为占位符，不得在成稿中还原：

- 报告单位、主管部门、关联单位的名称；
- 具体 IP 地址、域名、端口、系统名称；
- 具体日期、时间段、人员姓名或岗位；
- 具体软件名称、攻击工具、漏洞细节；
- 公章、签发人、联系方式。

成稿只保留“事件主体、相对方、事件类型、时间线、影响、处置、整改”这些结构性信息。真实项目使用时，由用户提供脱敏后的事实，或由模型留占位。
